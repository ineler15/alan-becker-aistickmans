Ported the [[sn_proto_wasm_renderer]] WASM prototype's approach into the Android app natively (Kotlin, no WASM) so "Red" renders as a procedural rig instead of raster sprites — new files under `android-app/app/src/main/java/com/stickmanai/android/overlay/`:

- `RigModel.kt` — `RigNode`/`RigFigure`, parses `assets/rigs/<id>.json` (a hand-slimmed JSON, NOT the full Stick Nodes schema — fields are `t/a/l/th/sc/usc/c/hollow/outline/oc/ch`). Only `rigs/Red.json` exists so far, generated once by running the sn-proto WASM parser in the browser and copying its (minimized) JSON output.
- `RigLayout.kt` — `Bone` data class + `layout()` (angle-accumulation walk, same math as the JS prototype) + `circleCenter()`/`CIRCLE_RADIUS_FACTOR` (0.65) for the head, matching the bug fixes recorded in [[sn_proto_wasm_renderer]].
- `RigView.kt` — custom `View.onDraw()` that fits-and-centers the pose using the REST pose's bounding box for scale (so switching poses doesn't visibly zoom the character), only translating per-pose.
- `PoseLibrary.kt` — bone paths are child-index lists (`listOf(0)` etc., since `.nodes` files carry no bone names) hardcoded for Red's specific topology (2 legs, spine, 2 arms, head) - only valid for rigs sharing that exact structure. Poses are angle-override maps, either static (STAND, SIT) or procedural/frame-driven (walk/run/bounce/trip/fall/pinch/angry/climb, via sine-wave swings around Red's rest angles). None of these except STAND are matched against a real reference - Stick Nodes only gave us one static pose per character, so they're first approximations tuned by eye/on-device, not ground truth.
- `CharacterOverlay.kt` — picks `RigView` over the old `ImageView`+`SpriteSet` path when `RigFigure.forCharacterOrNull()` finds a rig asset for that character id; every other character is untouched (still sprites).
- `CharacterState.kt` — added `FrameKind.Sit`, `.Angry(frame)`, `.Climb(frame)`, and wall-climbing physics: reaching x=0 or x=screenWidth while walking now triggers `startClimbing()` (climbs to a random y in the top half of the screen, then falls) instead of just stopping - mirrors vanilla Shimeji's ClimbWall behavior. `characterView.rotation` is set to ±90° while climbing (mirrors classic Shimeji's wall-cling animation), based on `state.climbSide`.
- `ActionsSchema.kt` / `OverlayService.kt` — `set_animation` gained `"sit"` and `"angry"` as valid emotional states end-to-end.

**Why:** user wants to eventually replace the sprite-PNG rendering across the app with rig-driven procedural animation; Android was chosen to go first since it's the only platform with its sprite assets actually committed to this repo (Java desktop and the web frontend both depend on an external already-built jar's `img/` folder that isn't in the repo - see [[project_overview]] if it exists, or the git history around the Shimeji sprite investigation).

**How to apply:** Validated live on the user's physical tablet via `adb install -r` + `adb shell screencap` (see [[windows_dev_workflow]] for the corrected `JAVA_HOME` path and MSYS path-conversion gotcha) - confirmed Stand and the Walk gait cycle render correctly at a stable scale with no crashes. Sit/Bounce/Trip/Fall/Pinch/Angry/Climb are implemented with the same mechanism but NOT yet visually confirmed on-device (no way to trigger them without either the AI actually deciding to, or physically dragging/walking the character to a screen edge) - don't assume their tuning is final; expect to retune `PoseLibrary`'s angle constants after actually seeing them. The pinch/dangle pose specifically WAS checked against the real `pinch01-07.png` sprite reference images for Red (legs pulled together, arms close to the torso, whole body swaying as one instead of each limb independently) rather than guessed from scratch.

**Expanded to 8 more characters on 2026-08-16** (`rigs/Blue.json`, `Green.json`, `Yellow.json`, `Purple.json`, `TCO.json`, `TDL.json`, `Orange.json` = narratively The Second Coming, `victim.json`) - generated by a one-off Node script (`gen-rigs.js`, in the session scratchpad, not committed) that runs the sn-proto WASM parser directly via `initSync({module: fs.readFileSync(...)})` instead of round-tripping through a browser tab - much faster than how Red's was made. Ported both the [[sn_proto_wasm_renderer]] head fixes (skip thickness<=0 bones, smooth-stroke consecutive curve-radius chains instead of drawing each segment straight) into `RigLayout.kt`/`RigView.kt`, since 4 of these 8 build their head from a segment ring rather than a Circle node and would otherwise show the same octagon-plus-stray-line bugs found on the web prototype.

Comparing each rig's node-type tree shape found that **Blue, Green, and Yellow are byte-for-byte the same topology as Red** (just recolored) - `PoseLibrary.forFrameKind`'s character gate now includes all four, so those three get full walk/sit/run/etc. poses for free, no per-character mapping needed. Purple has a genuinely different tree shape (its Circle/arms hang off root's *first* child instead of the third) and remains unmapped/stand-only.

**TCO/Orange and TDL/victim also mapped (2026-08-16), each needing their own fix:**
- TCO and Orange (The Second Coming) share Red's exact bone-path topology (`STANDARD_PATHS`) but were authored with a different limb orientation - added a second `RestAngles` set (`TCO_TOPOLOGY_REST`) rather than a second path set. This exposed two bugs in poses that weren't actually rest-relative despite taking a `rest` parameter: `SIT` was hardcoded to absolute angles tuned only for Red (the compiler had been flagging the unused parameter this whole time), and `PINCH`'s blend-toward-270 used plain linear subtraction instead of shortest-arc interpolation - for TCO's rest angles (numerically far from 270, though not far on the circle) that took the "long way around" and landed on something that read as a sit pose instead of dangling (a real user-reported bug: "cuando lo agarras tiene animación de sentado"). Both fixed to be genuinely rest-relative (`sitPose` now derives from Red's original deltas; added a `blendToward()` helper for the pinch blend).
- TDL and victim share TCO/Orange's exact rest angles, but their `.nodes` trees were serialized with a different child order (root -> [torso-chain, leg2, leg1] instead of [leg1, leg2, torso-chain]; neck hub -> [head-stalk, arm2, arm1] instead of [arm1, arm2, head-stalk]) - same rig family, different order. `PoseLibrary` was refactored around a `RigProfile(paths, rest)` pair instead of just rest angles, with a second `ALT_PATHS` bone-path set for these two.

`PoseLibrary.forFrameKind` is now keyed by a `PROFILE_BY_ID` map covering Red/Blue/Green/Yellow/TCO/Orange/TDL/victim (8 of 9 rig characters - only Purple remains unmapped/stand-only). Only verified visually as *not broken* (correct proportions, no crashes) while standing still on-device - couldn't confirm live walk/sit/pinch cycles for most of these because only Red has a real Gemini key configured on this device; the rest use the shared/blank key and never get an AI decision, so they never move to begin with (expected, not a rendering bug).
